# 当前供应链大脑构造

本文描述 **IR 供应链控制塔** 在现有代码中的实际构造：它如何感知各执行系统、如何形成记忆与判断、以及如何把指令发回肢体系统。内容以仓库现状为准，不是规划稿。

- IR 仓库：本项目（后端 `8090`，前端 `5174`）
- 阅读对象：后续要在 IR 上扩展大脑能力的人
- 依据：各系统 README 与 IR 后端包 `com.ir.*`

---

## 1. 一句话定位

IR 是坐在订单 / 仓储 / 运输 / 计费之上的 **控制塔**，不是再做一套 OMS 或 WMS。

执行系统各自记账、履约、计费；IR 只做四件事：

1. **拉事实**：把 OMS / WMS / TMS / BMS 的单据与库存拉成快照
2. **看全局**：看板、全链路追踪、成本
3. **做判断**：规则预警、需求预测、补货建议、沙盘推演
4. **发指令**：把建议变成对 OMS / WMS / TMS 的动作（SRM 仅生成采购建议，尚未真下单）

```text
需求侧                履约侧                 供应侧                财务侧
CRM / DMS             OMS → WMS → TMS        SRM / BOM / SAP       BMS / INV / OA
  线索·经销商              订单·仓·运              寻源·零件·ERP          计费·发票·审批
                              │
                              ▼
                     ┌─────────────────┐
                     │   IR 控制塔     │  ← 当前供应链大脑
                     │  感知 · 记忆 ·  │
                     │  认知 · 执行    │
                     └─────────────────┘
```

## 2. 集团系统全景：谁是肢体、谁是大脑

当前工作区共 12 个同构系统（Spring Boot + Vue 3）。IR 只直接接入其中 4 个，预留 1 个。

| 系统 | 角色 | 在供应链里做什么 | 与 IR 的关系 |
| --- | --- | --- | --- |
| **OMS** | 订单中枢 | 多渠道接单、审核、分仓、库存预占、推 WMS、售后 | **已接入**：订单 / 可售库存 / 日销量；可下发改仓、挂起、加急、取消 |
| **WMS** | 仓储执行 | ASN 收货上架、出库分配拣货发运、库内作业 | **已接入**：出库单 / 库存汇总；可下发分配、仓内补货 |
| **TMS** | 运输执行 | 运单调度、在途、围栏、三方物流、运费 | **已接入**：运单 / 运费账单；可下发调度、轨迹同步、换承运商 |
| **BMS** | 计费结算 | 按合同费率给 WMS/TMS/OMS 单据计 AR/AP | **已接入客户端**：拉近 90 天成本；BMS 侧 `GET /api/open/cost/records` **尚未上线** |
| **SRM** | 供应协同 | PR→RFQ→PO→ASN→WMS 收货→三单匹配发票 | **预留**：`ct_system` 中 `enabled=false`；补货只生成建议，不调 SRM |
| **SAP** | ERP | MM/SD/FI/CO/PP，P2P / O2C / 生产过账 | 未接入 IR；与 SRM / BMS 有独立集成 |
| **BOM** | 产品结构 | EBOM/MBOM/SBOM、ECR/ECN、同步 SAP | 未接入 IR |
| **CRM** | 需求入口 | 线索、客户、商机、工单 | 未接入 IR |
| **DMS** | 经销商 | 整车销售、维修、备件；向 OMS 下补货单 | 未接入 IR；经 OMS 间接进入订单流 |
| **INV** | 发票税务 | 销项/进项/属期申报；接 OMS/BMS/SRM | 未接入 IR |
| **OA** | 组织协同 | 人事考勤审批工资；OAuth 给 SAP/SRM/CRM | 未接入 IR |
| **IR** | **大脑** | 快照、看板、追踪、预警、预测、沙盘、指令 | 本系统 |

### 2.1 执行层已经存在的主链路（不经过 IR）

这些链路在各系统 Open API 里已经跑通，IR **不参与记账**，只事后拉快照观察。

```text
渠道 / DMS                供应商
   │                        │
   │ Open API 下单           │ ASN
   ▼                        ▼
 OMS 审核·分仓·预占      SRM 寻源·PO·ASN
   │ 推送出库单              │ 同步入库单
   ▼                        ▼
 WMS 分配·拣货·打包·发运  WMS 收货·上架
   │ 发货回传 / 创建运单     │ 收货回传 → GR → SAP MIGO
   ▼                        ▼
 TMS 调度·在途·签收        SAP 库存 / 应付
   │ 签收回传 OMS            │
   ▼                        ▼
 OMS COMPLETED            BMS 计费 → INV 开票
   │
   └── 单据量纲 ──▶ BMS（入库/出库/仓储/运输/VAS/退货）
```

IR 要成为大脑，靠的不是插入这条链路，而是 **站在链路上层做感知与干预**。

## 3. 大脑分层

IR 后端按包拆成四层，对应感知 → 记忆 → 认知 → 运动。

```text
┌──────────────────────────────────────────────────────────────┐
│ 前端 Vue3 :5174                                               │
│ 控制塔 / 追踪 / 预警 / 规则 / 指令 / 预测 / 补货 / 沙盘 / 成本 │
└────────────────────────────┬─────────────────────────────────┘
                             │ /api  →  :8090
┌────────────────────────────▼─────────────────────────────────┐
│ 运动层  com.ir.action                                         │
│   ActionService：把指令打到 OMS/WMS/TMS，并回写本地快照        │
├──────────────────────────────────────────────────────────────┤
│ 认知层                                                        │
│   tower     看板 KPI / 漏斗 / 仓负荷                          │
│   trace     订单跨 OMS-WMS-TMS 拼接                           │
│   alert     规则引擎 + 建议动作                               │
│   forecast  时序预测 + 补货                                   │
│   sandbox   仓配/需求/承运商沙盘                              │
│   cost      成本汇总 / 目标 / 指令节约                        │
├──────────────────────────────────────────────────────────────┤
│ 记忆层  com.ir.snapshot                                       │
│   订单 / 出库 / 运单 / 库存 / 日销 / 成本  六张快照表          │
├──────────────────────────────────────────────────────────────┤
│ 感知层  com.ir.integration                                    │
│   ClientFactory：MOCK | HTTP                                  │
│   SyncService：启动补齐 + 每 5 分钟拉数 + 健康检查             │
└───────────┬──────────┬──────────┬──────────┬─────────────────┘
            ▼          ▼          ▼          ▼
          OMS        WMS        TMS        BMS     （SRM 禁用预留）
```

启动时 `IrApplication` 做三步热身：快照为空则 `syncAll()` → `alertEngine.evaluate()` → `sandboxService.ensureBaseline()`。调度默认 `0 0/5 * * * ?`（可用 `ir.sync.cron` 覆盖）。

## 4. 感知层：怎么把肢体系统读进来

### 4.1 系统注册表 `ct_system`

种子数据（`data.sql`）预置：

| code | 名称 | 默认 URL | 认证 | mode | enabled |
| --- | --- | --- | --- | --- | --- |
| OMS | 订单管理系统 | `http://localhost:8081` | BEARER | MOCK | 是 |
| WMS | 仓储管理系统 | `http://localhost:8083` | BEARER | MOCK | 是 |
| TMS | 运输管理系统 | `http://localhost:8082` | NONE | MOCK | 是 |
| BMS | 计费系统 | `http://localhost:8084` | API_KEY | MOCK | 是 |
| SRM | 供应商管理系统（预留） | 空 | NONE | MOCK | **否** |

`mode=MOCK` 时走 `com.ir.integration.mock.*`，用固定种子 `Random(20250301L)` 生成约 300 张演示订单及配套出库、运单、库存、日销、成本。`mode=HTTP` 时 `ClientFactory` 现场 `new` 对应 `Http*Client`。

### 4.2 每次同步拉什么

`SyncService.sync(code)` 按系统分流：

| 系统 | 拉取 | 落入 |
| --- | --- | --- |
| OMS | `fetchOrders` / `fetchInventory` / `fetchDailySales(90)` | `ct_order_snapshot`、`ct_inventory_snapshot(source=OMS)`、`ct_sales_daily` |
| WMS | `fetchOutbound` / `fetchInventorySummary` | `ct_wms_order_snapshot`、`ct_inventory_snapshot(source=WMS)` |
| TMS | `fetchWaybills` / `fetchFreightBills` | `ct_shipment_snapshot`、`ct_cost_record(source=TMS)` |
| BMS | `fetchCosts(today-90, today)` | `ct_cost_record(source=BMS)` |

幂等策略：

- 订单 / 出库 / 运单：按业务单号查到则更新，否则插入
- 库存：`(source_system, warehouse_code, sku)` 唯一
- 日销：`(sales_date, sku, warehouse_code, channel_code)` 唯一
- **成本：先按 `source_system` 整表删除再插入**（TMS / BMS 各自一套）

HTTP 端点约定（来自各系统现有页面接口，不是独立的控制塔 API）：

| 系统 | 读 | 写（指令） |
| --- | --- | --- |
| OMS | `/api/order/page`、`/api/inventory/page`、`/api/report/order-daily`、`/api/dashboard` | `/api/order/{no}/hold\|unhold\|allocate\|auto\|cancel\|remark` |
| WMS | `/api/outbound/order/page`、`/api/inventory/summary`、`/api/dashboard` | `/api/outbound/order/{code}/allocate`、`/api/inventory/replenish/generate` |
| TMS | `/api/waybill/page`、`/api/billing/page`、`/api/dashboard` | `/api/waybill/{id}/dispatch`、`/sync-track` |
| BMS | `/api/open/cost/records?from&to`（约定，BMS 仓库尚未实现） | 无（BMS 客户端没有 `execute`） |

同步与健康检查结果写 `ct_sync_log`，并回写 `ct_system.last_health_*`。

## 5. 记忆层：快照才是大脑的工作记忆

IR **没有**自己的订单状态机。认知层全部读这六张事实表：

| 表 | 关联键 | 主要内容 |
| --- | --- | --- |
| `ct_order_snapshot` | `order_no` | 渠道、仓、省市区、状态、金额、下单/支付/发货/完成时间、承运商 |
| `ct_wms_order_snapshot` | `code`，`external_no` = OMS 单号 | 仓、拣货/发运数量、打包/发运时间 |
| `ct_shipment_snapshot` | `waybill_code`，`source_no` = OMS 单号 | 承运商、计划/实际到达、运费、异常标记 |
| `ct_inventory_snapshot` | 仓 + SKU + 来源系统 | 在库 / 预占 / 可用 / 安全库存 |
| `ct_sales_daily` | 日 + SKU + 仓 + 渠道 | 销量与金额（预测的历史输入） |
| `ct_cost_record` | 日期 + 可选订单/仓/承运商 | `cost_type` + 金额 + 来源系统 |

追踪拼接方式（`TraceService`）：

```text
OMS.orderNo  ──external_no──▶  WMS 出库单
             ──source_no  ──▶  TMS 运单
             ──order_no   ──▶  成本 / 预警 / 指令
```

阶段判定：`CANCELLED` → 已取消；运单已签收 → `DELIVERED`；有运单 → `TRANSPORT`；有出库单 → `WAREHOUSE`；否则 `ORDER`。

卡单小时：

- OMS `AUDITED` 超过 4 小时
- WMS `PICKING` 超过 6 小时
- TMS 计划到达已过且未签收

演示数据里 OMS 仓编码是 `WH-SH / WH-BJ / WH-GZ`，WMS 仓编码是 `WH01 / WH02 / WH03`。两套库存快照按 `source_system` 并存，看板仓负荷目前按 OMS 三仓硬编码统计。

## 6. 认知层：六块皮层

### 6.1 控制塔看板 `com.ir.tower`

`GET /api/tower/overview` 一次算出：

- KPI：今日订单、未完成订单、在途、延误运单、低库存 SKU、未关闭预警、近 30 天成本、单均成本、OTIF、平均履约小时
- 漏斗：OMS / WMS / TMS 状态计数
- 成本趋势：近 30 天按日、按费用类型
- 仓负荷：`WH-SH / WH-BJ / WH-GZ` 的待发订单、库存量、低库存 SKU
- 最新 10 条 OPEN 预警、各系统健康

OTIF 定义：已送达运单中，`actualArriveTime <= plannedArriveTime` 的比例。低库存：`qtyAvailable < safetyQty`。

### 6.2 全链路追踪 `com.ir.trace`

列表按 OMS 订单分页，详情带时间线、该单成本、相关预警与指令。这是大脑把三条执行链「看成一张订单」的入口。

### 6.3 规则预警 `com.ir.alert`

规则存在 `ct_rule`，评估时只跑 `enabled=true`。同一规则 + 同一 `target_key` 已有 OPEN 预警则不重复建。

内置规则：

| 编码 | 类型 | 条件 | 建议动作 |
| --- | --- | --- | --- |
| `OMS_STUCK` | `ORDER_STUCK` | 状态 `AUDITED` 超过 4 小时 | `OMS_HOLD` |
| `UNSHIPPED_ORDER` | `ORDER_STUCK` | 状态 `PAID` 超过 24 小时 | `OMS_PRIORITIZE` |
| `WMS_STUCK` | `WMS_STUCK` | 出库单 `PICKING` 且对应 OMS 单超过 6 小时 | `WMS_ALLOCATE` |
| `TMS_DELAY` | `TMS_DELAY` | 计划到达已过且未签收 | `TMS_SYNC_TRACK` |
| `EXCEPTION_SHIPMENT` | `TMS_DELAY` | `exceptionFlag=true` | `TMS_SYNC_TRACK` |
| `LOW_STOCK` | `LOW_STOCK` | 可用 < 安全库存 | `SRM_PURCHASE_SUGGEST` |
| `COST_OVERRUN` | `COST_OVERRUN` | 近 N 天仓维度单均成本超过阈值 | `TMS_SWITCH_CARRIER` |
| `FORECAST_STOCKOUT` | `FORECAST_STOCKOUT` | 补货模型算出的缺货日落在 horizon 内 | `SRM_PURCHASE_SUGGEST` |

预警状态：`OPEN → ACKED / RESOLVED / IGNORED`。`execute-suggested` 会按规则上的建议动作调 `ActionService.createAndExecute`，并把 `action_id` 回写预警。

### 6.4 需求预测与补货 `com.ir.forecast`

输入是 `ct_sales_daily` 近 90 天按日求和。算法在 `ForecastEngine`：

| 方法 | 含义 |
| --- | --- |
| `MA` | 7 日滑动平均，滚动外推 |
| `SES` | 简单指数平滑，α=0.3，水平值持平外推 |
| `HOLT` | 带趋势指数平滑，α=0.3、β=0.1 |
| `SEASONAL_NAIVE` | 周期 7，取近 4 个同星期均值 |
| `AUTO` | 对上述四法做最近最多 14 天 holdout MAPE，选最小者 |

预测带 ±1.28σ 残差区间（约 80% 带宽）。每次 `run` 落 `ct_forecast`。

补货公式（仓+SKU）：

```text
horizon 内预测需求 demand
日均 daily = demand / horizon
安全库存 safety = daily × serviceDays（默认 3）
建议量 suggestQty = max(0, demand + safety − qtyAvailable)
缺货日 = 今日 + floor(qtyAvailable / daily)
```

`inTransit` 当前恒为 0。补货行可一键转成 `SRM_PURCHASE_SUGGEST` 指令。

### 6.5 沙盘 `com.ir.sandbox`

用当前库存快照 + 日销 + 订单省份分布做 **基线**，再改参数重跑，对比成本与服务水平。仓库集合写死为 `WH-SH / WH-BJ / WH-GZ`。

可调参数（`ScenarioParams`）：

- 推演天数、总需求倍率、分渠道需求倍率
- 分仓策略：`NEAREST` / `LOWEST_COST` / `BALANCED` / `SINGLE_WAREHOUSE`
- 承运商配比与费率（默认 SF 0.4 / JDL 0.3 / SELF 0.3）
- 安全天数、补货提前期、期初库存倍率
- 仓储 / 操作 / 包材 / 缺货惩罚单价

日循环：到货 → 按区域需求选仓发货 → 累计运费/操作/包材/仓储/缺货罚 → 按安全天数生成在途补货。需求外推用 `seasonalNaive`。

`apply` **不直接改执行系统**，只生成待执行指令：

- 策略变成单仓或最低成本 → 按 SKU 生成 `OMS_REROUTE_WAREHOUSE`
- 承运商配比相对基线变化 → 生成 `TMS_SWITCH_CARRIER`
- 场景仍有缺货件数 → 按 SKU 生成 `SRM_PURCHASE_SUGGEST`

### 6.6 成本 `com.ir.cost`

读 `ct_cost_record`：按类型 / 仓 / 承运商 / 日期汇总，对照 `ct_cost_target` 做目标 vs 实际。节约金额来自状态 `SUCCESS` 的指令上的 `expectedSaving`（人工填，不是系统算出来的）。

## 7. 运动层：大脑如何动手

`ActionService` 是唯一出口。指令类型前缀决定落点：

| 类型 | 目标系统 | 作用 |
| --- | --- | --- |
| `OMS_REROUTE_WAREHOUSE` | OMS | 改分配仓，并回写订单快照的 `warehouseCode` |
| `OMS_HOLD` / `OMS_UNHOLD` | OMS | 挂起 / 解挂 |
| `OMS_PRIORITIZE` | OMS | 加急（HTTP 落到 remark） |
| `OMS_AUTO_PROCESS` | OMS | 一键处理 |
| `OMS_CANCEL` | OMS | 取消，快照状态改为 `CANCELLED` |
| `WMS_ALLOCATE` | WMS | 出库分配，快照状态改为 `ALLOCATED` |
| `WMS_REPLENISH` | WMS | 触发仓内 Min/Max 补货任务 |
| `TMS_DISPATCH` | TMS | 调度发车 |
| `TMS_SYNC_TRACK` | TMS | 拉轨迹 |
| `TMS_SWITCH_CARRIER` | TMS | 换承运商（HTTP 复用 dispatch），回写运单快照 |
| `SRM_PURCHASE_SUGGEST` | SRM | **不外调**，结果固定为「SRM 未接入，已生成采购建议」 |

闭环：

```text
快照变化 ─▶ 规则/预测/沙盘 ─▶ 预警或场景
                              │
                              ▼
                     建议动作 / apply
                              │
                              ▼
                     ct_action  PENDING
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        HTTP/MOCK execute               回写本地快照
              │
              ▼
         SUCCESS / FAILED  （可 retry 再下一张新指令）
```

角色：`ADMIN` / `PLANNER` 可写，`VIEWER` 只读。前端按角色藏按钮，后端仍走登录 Bearer。

## 9. 当前边界（写代码时必须当成约束）

这些不是待办清单，是 **现在这颗大脑实际长到哪**。

1. **只观察履约四件套**：OMS / WMS / TMS / BMS。需求侧 CRM/DMS、供应侧 SRM/BOM/SAP、财务侧 INV/OA 都不在同步列表里。
2. **以拉为主**：5 分钟 cron + 手工同步，没有 webhook / 消息总线。执行系统状态变了，大脑最多延迟一个周期。
3. **快照不是账本**：IR 改快照（取消、改仓）不会保证与源系统最终一致；源系统才是权威。
4. **SRM 是断的**：低库存、预测缺货、沙盘缺货最后都停在「采购建议」单据上。
5. **BMS 成本 HTTP 口未落地**：客户端已写 `GET /api/open/cost/records`，BMS 仓库当前 Open API 只有单据推送，没有成本查询。
6. **仓编码两套**：看板和沙盘用 OMS 仓号；WMS 库存是另一套编码。跨系统库存对账还没有统一主数据。
7. **在途不计入补货**：`inTransit` 恒 0，建议量会偏大。
8. **沙盘 apply 生成的是 PENDING 指令**，不会自动 `execute`。
9. **成本节约依赖人工 `expectedSaving`**，不能当成真实 P&L。

## 11. 读完后应形成的图景

当前供应链的「身体」已经按专业系统拆开：OMS 接单、WMS 作业、TMS 在途、SRM 采购、BMS 算钱。  
当前供应链的「大脑」是 IR：用快照做工作记忆，用规则/预测/沙盘做判断，用指令试图反向驱动履约三系统。

它已经具备控制塔的骨架（感知、可视化、预警、推演、部分闭环），但还不是覆盖需求-供应-财务的完整中枢：供应建议到不了 SRM，成本 HTTP 还没接到 BMS，需求侧与 ERP 也还没进快照。
