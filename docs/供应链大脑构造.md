# 当前供应链大脑构造

本文描述 **IR 供应链控制塔** 在现有代码中的实际构造：它如何感知各执行系统、如何形成记忆与判断、以及如何把指令发回肢体系统。内容以仓库现状为准，不是规划稿。

- IR 仓库：本项目（后端 `8090`，前端 `5174`）
- 阅读对象：后续要在 IR 上扩展大脑能力的人
- 依据：各系统 README 与 IR 后端包 `com.ir.*`

---

## 1. 一句话定位

IR 是坐在订单 / 仓储 / 运输 / 计费 / 供应 / ERP 之上的 **控制塔**，不是再做一套 OMS 或 WMS。

执行系统各自记账、履约、计费；IR 只做四件事：

1. **拉事实**：把 OMS / WMS / TMS / BMS 以及 SRM / SAP / BOM / INV / CRM / DMS / OA 的单据拉成快照
2. **看全局**：看板、全链路追踪、成本、生态单据
3. **做判断**：规则预警、需求预测、补货建议、沙盘推演
4. **发指令**：把建议变成对各执行系统的动作（沙盘可选择只生成待执行指令，或立即执行）

```text
需求侧                履约侧                 供应侧                财务侧
CRM / DMS             OMS → WMS → TMS        SRM / BOM / SAP       BMS / INV / OA
  线索·经销商              订单·仓·运              寻源·零件·ERP          计费·发票·审批
                              │
                              ▼
                     ┌─────────────────┐
                     │   IR 控制塔     │  ← 当前供应链大脑
                     │  感知 · 记忆 ·  │
                     │  认知 · 执行    │
                     └─────────────────┘
```

## 2. 集团系统全景：谁是肢体、谁是大脑

当前工作区共 12 个同构系统（Spring Boot + Vue 3）。IR 通过 `ct_system` 注册并同步全部 11 个执行系统。

| 系统 | 角色 | 在供应链里做什么 | 与 IR 的关系 |
| --- | --- | --- | --- |
| **OMS** | 订单中枢 | 多渠道接单、审核、分仓、库存预占、推 WMS、售后 | **已接入**：订单 / 可售库存 / 日销量；可下发改仓、挂起、加急、取消 |
| **WMS** | 仓储执行 | ASN 收货上架、出库分配拣货发运、库内作业 | **已接入**：出库单 / 库存汇总；可下发分配、仓内补货 |
| **TMS** | 运输执行 | 运单调度、在途、围栏、三方物流、运费 | **已接入**：运单 / 运费账单；可下发调度、轨迹同步、换承运商 |
| **BMS** | 计费结算 | 按合同费率给 WMS/TMS/OMS 单据计 AR/AP | **已接入**：拉近 90 天成本 |
| **SRM** | 供应协同 | PR→RFQ→PO→ASN→WMS 收货→三单匹配发票 | **已接入**：PR / PO / ASN 快照；采购建议、提交/审批 PR |
| **SAP** | ERP | MM/SD/FI/CO/PP，P2P / O2C / 生产过账 | **已接入**：库存 / PR / PO / 生产订单；创建/释放 PR、释放工单 |
| **BOM** | 产品结构 | EBOM/MBOM/SBOM、ECR/ECN、同步 SAP | **已接入**：BOM / ECN 快照；BOM 展开 |
| **CRM** | 需求入口 | 线索、客户、商机、工单 | **已接入**：商机 / 工单快照；推进商机、升级工单 |
| **DMS** | 经销商 | 整车销售、维修、备件；向 OMS 下补货单 | **已接入**：缺货 / 补货单快照；按缺货生成补货单 |
| **INV** | 发票税务 | 销项/进项/属期申报；接 OMS/BMS/SRM | **已接入**：开票申请快照；提交 / 审核申请 |
| **OA** | 组织协同 | 人事考勤审批工资；OAuth 给 SAP/SRM/CRM | **已接入**：审批实例 / 待办快照；发起采购审批 |
| **IR** | **大脑** | 快照、看板、追踪、预警、预测、沙盘、指令 | 本系统 |

### 2.1 执行层已经存在的主链路（不经过 IR）

这些链路在各系统 Open API 里已经跑通，IR **不参与记账**，只事后拉快照观察。

```text
渠道 / DMS                供应商
   │                        │
   │ Open API 下单           │ ASN
   ▼                        ▼
 OMS 审核·分仓·预占      SRM 寻源·PO·ASN
   │ 推送出库单              │ 同步入库单
   ▼                        ▼
 WMS 分配·拣货·打包·发运  WMS 收货·上架
   │ 发货回传 / 创建运单     │ 收货回传 → GR → SAP MIGO
   ▼                        ▼
 TMS 调度·在途·签收        SAP 库存 / 应付
   │ 签收回传 OMS            │
   ▼                        ▼
 OMS COMPLETED            BMS 计费 → INV 开票
   │
   └── 单据量纲 ──▶ BMS（入库/出库/仓储/运输/VAS/退货）
```

IR 要成为大脑，靠的不是插入这条链路，而是 **站在链路上层做感知与干预**。

## 3. 大脑分层

IR 后端按包拆成四层，对应感知 → 记忆 → 认知 → 运动。

```text
┌──────────────────────────────────────────────────────────────┐
│ 前端 Vue3 :5174                                               │
│ 控制塔 / 追踪 / 预警 / 规则 / 指令 / 预测 / 补货 / 人工沙盘 / 自动沙盘 / 成本 │
└────────────────────────────┬─────────────────────────────────┘
                             │ /api  →  :8090
┌────────────────────────────▼─────────────────────────────────┐
│ 运动层  com.ir.action                                         │
│   ActionService：把指令打到 OMS/WMS/TMS/SRM/SAP/BOM/INV/CRM/DMS/OA │
├──────────────────────────────────────────────────────────────┤
│ 认知层                                                        │
│   tower     看板 KPI / 漏斗 / 仓负荷 / 生态单据                │
│   trace     订单跨 OMS-WMS-TMS，并挂生态单据 / 供应风险        │
│   alert     规则引擎 + 跨系统建议动作                         │
│   forecast  时序预测 + 补货                                   │
│   sandbox   人工沙盘 + 系统自动沙盘（成本/效率综合分）          │
│   cost      成本汇总 / 目标 / 指令节约                        │
├──────────────────────────────────────────────────────────────┤
│ 记忆层  com.ir.snapshot                                       │
│   订单 / 出库 / 运单 / 库存 / 日销 / 成本 / 生态快照            │
├──────────────────────────────────────────────────────────────┤
│ 感知层  com.ir.integration                                    │
│   ClientFactory：MOCK | HTTP                                  │
│   SyncService：启动补齐 + 每 5 分钟拉数 + 健康检查             │
└───────────┬──────────┬──────────┬──────────┬─────────────────┘
            ▼          ▼          ▼          ▼
          OMS        WMS        TMS        BMS
          SRM        SAP        BOM        INV
          CRM        DMS        OA
```

启动时 `IrApplication` 做四步热身：快照为空则 `syncAll()` → `alertEngine.evaluate()` → `sandboxService.ensureBaseline()` → 若 `ir.sandbox.auto-on-startup=true` 则跑一轮系统自动沙盘。调度默认 `0 0/5 * * * ?`（可用 `ir.sync.cron` 覆盖）；自动沙盘另有 `ir.sandbox.auto-cron`（默认每 6 小时 30 分）。

## 4. 感知层：怎么把肢体系统读进来

### 4.1 系统注册表 `ct_system`

种子数据（`data.sql`）预置：

| code | 名称 | 默认 URL | 认证 | mode | enabled |
| --- | --- | --- | --- | --- | --- |
| OMS | 订单管理系统 | `http://localhost:8081` | BEARER + `oms-open-key` | MOCK | 是 |
| WMS | 仓储管理系统 | `http://localhost:8083` | BEARER + `wms-open-key` | MOCK | 是 |
| TMS | 运输管理系统 | `http://localhost:8082` | NONE | MOCK | 是 |
| BMS | 计费系统 | `http://localhost:8084` | API_KEY `bms-open-key` | MOCK | 是 |
| SRM | 供应商管理系统 | `http://localhost:8087` | API_KEY `srm-wms-key` | MOCK | 是 |
| SAP | ERP 系统 | `http://localhost:8085` | API_KEY `sap-open-key` | MOCK | 是 |
| OA | 协同办公 | `http://localhost:8086` | API_KEY `oa-open-key` | MOCK | 是 |
| BOM | 产品结构 | `http://localhost:8088` | API_KEY `bom-open-key` | MOCK | 是 |
| INV | 发票税务 | `http://localhost:8089` | API_KEY `inv-open-key` | MOCK | 是 |
| CRM | 客户关系 | `http://localhost:8091` | API_KEY `crm-open-key` | MOCK | 是 |
| DMS | 经销商系统 | `http://localhost:8092` | API_KEY `dms-open-key` | MOCK | 是 |

`mode=MOCK` 时走 `com.ir.integration.mock.*`，用固定种子 `Random(20250301L)` 生成约 300 张演示订单及配套出库、运单、库存、日销、成本。`mode=HTTP` 时 `ClientFactory` 现场 `new` 对应 `Http*Client`。启动参数 `IR_HTTP_SYSTEMS=SAP,OA,SRM`（或 `*`）会在启动时把对应 `ct_system.mode` 写成 `HTTP`，不必进界面逐个改。

联调链路（真实开放口，不是 MOCK）：

1. 同步 SAP → 种子物料 `M1099` 别名 `MAT-1000` 库存 3 → `SAP_LOW_STOCK`
2. 执行建议 → `SAP_CREATE_PR` + `SRM_PURCHASE_SUGGEST` + `OA_START_WORKFLOW` + `WMS_REPLENISH`
3. 再同步 OA → `WF_TASK PENDING` → `OA_WF_PENDING`
4. 执行建议 → `OA_APPROVE_TASK`（按待办自己的审批人过账，不新开流程）


### 4.2 每次同步拉什么

`SyncService.sync(code)` 按系统分流：

| 系统 | 拉取 | 落入 |
| --- | --- | --- |
| OMS | `fetchOrders` / `fetchInventory` / `fetchDailySales(90)` | `ct_order_snapshot`、`ct_inventory_snapshot(source=OMS)`、`ct_sales_daily` |
| WMS | `fetchOutbound` / `fetchInventorySummary` | `ct_wms_order_snapshot`、`ct_inventory_snapshot(source=WMS)` |
| TMS | `fetchWaybills` / `fetchFreightBills` | `ct_shipment_snapshot`、`ct_cost_record(source=TMS)` |
| BMS | `fetchCosts(today-90, today)` | `ct_cost_record(source=BMS)` |
| SRM / SAP / BOM / INV / CRM / DMS / OA | `GET /api/open/ir/snapshots` | `ct_ext_snapshot` |

幂等策略：

- 订单 / 出库 / 运单：按业务单号查到则更新，否则插入
- 库存：`(source_system, warehouse_code, sku)` 唯一
- 日销：`(sales_date, sku, warehouse_code, channel_code)` 唯一
- **成本：先按 `source_system` 整表删除再插入**（TMS / BMS 各自一套）

同步时仓编码统一映射到 OMS 口径：`WH01→WH-SH`、`WH02→WH-BJ`、`WH03→WH-GZ`（`WarehouseCodes`）。看板、沙盘、库存对账都按这套仓号工作；下发 WMS 补货时再映回 `WH01/02/03`。

HTTP 端点约定：

| 系统 | 读 | 写（指令，优先 Open IR） |
| --- | --- | --- |
| OMS | `/api/order/page`、`/api/inventory/page`、`/api/report/order-daily`、`/api/dashboard` | `POST /api/open/ir/actions`（HOLD/UNHOLD/REROUTE/AUTO/CANCEL/PRIORITIZE） |
| WMS | `/api/outbound/order/page`、`/api/inventory/summary`、`/api/dashboard` | `POST /api/open/ir/actions`（ALLOCATE/REPLENISH） |
| TMS | `/api/waybill/page`、`/api/billing/page`、`/api/dashboard` | `POST /api/open/ir/actions`（DISPATCH/SYNC_TRACK/SWITCH_CARRIER） |
| BMS | `GET /api/open/cost/records?from&to` | 无（BMS 客户端没有 `execute`） |
| SRM / SAP / BOM / INV / CRM / DMS / OA | `GET /api/open/ir/snapshots` | `POST /api/open/ir/actions` |

同步与健康检查结果写 `ct_sync_log`，并回写 `ct_system.last_health_*`。

## 5. 记忆层：快照才是大脑的工作记忆

IR **没有**自己的订单状态机。认知层全部读这些事实表：

| 表 | 关联键 | 主要内容 |
| --- | --- | --- |
| `ct_order_snapshot` | `order_no` | 渠道、仓、省市区、状态、金额、下单/支付/发货/完成时间、承运商 |
| `ct_wms_order_snapshot` | `code`，`external_no` = OMS 单号 | 仓、拣货/发运数量、打包/发运时间 |
| `ct_shipment_snapshot` | `waybill_code`，`source_no` = OMS 单号 | 承运商、计划/实际到达、运费、异常标记 |
| `ct_inventory_snapshot` | 仓 + SKU + 来源系统 | 在库 / 预占 / 可用 / 安全库存 |
| `ct_sales_daily` | 日 + SKU + 仓 + 渠道 | 销量与金额（预测的历史输入） |
| `ct_cost_record` | 日期 + 可选订单/仓/承运商 | `cost_type` + 金额 + 来源系统 |
| `ct_ext_snapshot` | `source_system` + `data_type` + `biz_key` | SRM/SAP/BOM/INV/CRM/DMS/OA 单据状态、SKU、数量、金额 |

追踪拼接方式（`TraceService`）：

```text
OMS.orderNo  ──external_no──▶  WMS 出库单
             ──source_no  ──▶  TMS 运单
             ──order_no   ──▶  成本 / 预警 / 指令
```

阶段判定：`CANCELLED` → 已取消；运单已签收 → `DELIVERED`；有运单 → `TRANSPORT`；有出库单 → `WAREHOUSE`；否则 `ORDER`。

卡单小时：

- OMS `AUDITED` 超过 4 小时
- WMS `PICKING` 超过 6 小时
- TMS 计划到达已过且未签收

演示数据里 OMS 仓编码是 `WH-SH / WH-BJ / WH-GZ`，WMS 仓编码是 `WH01 / WH02 / WH03`。两套库存快照按 `source_system` 并存，看板仓负荷目前按 OMS 三仓硬编码统计。

## 6. 认知层：六块皮层

### 6.1 控制塔看板 `com.ir.tower`

`GET /api/tower/overview` 一次算出：

- KPI：今日订单、未完成订单、在途（未签收运单）、延误运单、低库存 SKU、未关闭预警、近 30 天成本、单均成本、OTIF、平均履约小时
- 漏斗：OMS / WMS / TMS 状态计数
- 成本趋势：近 30 天按日、按费用类型
- 仓负荷：`WH-SH / WH-BJ / WH-GZ` 的待发订单、库存量、低库存 SKU
- 最新 10 条 OPEN 预警、各系统健康
- **自动沙盘推荐**：最近一轮系统自动沙盘中综合分最高的方案（成本分 + 效率分）

OTIF 定义：已送达运单中，`actualArriveTime <= plannedArriveTime` 的比例。低库存：`qtyAvailable < safetyQty`。

### 6.2 全链路追踪 `com.ir.trace`

列表按 OMS 订单分页，详情带时间线（OMS/WMS/TMS + 关联生态节点）、该单成本、相关预警与指令，以及：

- `ecosystem`：INV 开票、OA 审批等与订单号对得上的生态快照
- `supplyRisks`：当前 SAP 低库存 / SRM 草稿 PR / DMS 缺货 / OA 待办等供应侧风险

这是大脑把履约链和供应侧「看成一张订单」的入口。

### 6.3 规则预警 `com.ir.alert`

规则存在 `ct_rule`，评估时只跑 `enabled=true`。同一规则 + 同一 `target_key` 已有 OPEN 预警则不重复建。

内置规则：

| 编码 | 类型 | 条件 | 建议动作 |
| --- | --- | --- | --- |
| `OMS_STUCK` | `ORDER_STUCK` | 状态 `AUDITED` 超过 4 小时 | `OMS_HOLD` |
| `UNSHIPPED_ORDER` | `ORDER_STUCK` | 状态 `PAID` 超过 24 小时 | `OMS_PRIORITIZE` |
| `WMS_STUCK` | `WMS_STUCK` | 出库单 `PICKING` 且对应 OMS 单超过 6 小时 | `WMS_ALLOCATE` |
| `TMS_DELAY` | `TMS_DELAY` | 计划到达已过且未签收 | `TMS_SYNC_TRACK` |
| `EXCEPTION_SHIPMENT` | `TMS_DELAY` | `exceptionFlag=true` | `TMS_SYNC_TRACK` |
| `LOW_STOCK` | `LOW_STOCK` | 可用 < 安全库存 | `SRM_PURCHASE_SUGGEST` |
| `COST_OVERRUN` | `COST_OVERRUN` | 近 N 天仓维度单均成本超过阈值 | `TMS_SWITCH_CARRIER` |
| `DMS_PART_SHORTAGE` | `EXT_STATUS` | DMS 缺货快照 `SHORT` | `DMS_REPLENISH_SHORTAGE` |
| `SAP_LOW_STOCK` | `EXT_STATUS` | SAP 库存快照 `LOW` | `SAP_CREATE_PR` |
| `SAP_PR_OPEN` | `EXT_STATUS` | SAP PR `CREATED` | `SAP_RELEASE_PR` |
| `SRM_PR_DRAFT` | `EXT_STATUS` | SRM PR `DRAFT` | `SRM_SUBMIT_PR` |
| `INV_REQUEST_DRAFT` | `EXT_STATUS` | 开票申请 `DRAFT` | `INV_SUBMIT_REQUEST` |
| `CRM_STALE_OPP` | `EXT_STATUS` | 商机 `QUALIFICATION` | `CRM_ADVANCE_STAGE` |
| `CRM_OPEN_CASE` | `EXT_STATUS` | 工单 `NEW` | `CRM_ESCALATE_CASE` |
| `OA_WF_PENDING` | `EXT_STATUS` | OA 待办 `PENDING` | `OA_APPROVE_TASK` |

预警状态：`OPEN → ACKED / RESOLVED / IGNORED`。`execute-suggested` 会走 `CoordinationService`：先按快照补全 sku/qty/工厂，再按类型拆成一组跨系统指令（缺货类 → SRM 采购建议 + SAP 建 PR + OA 审批 + WMS 仓内补货；经销商缺货再加 DMS 补货单）。主指令 `action_id` 回写预警。

### 6.4 需求预测与补货 `com.ir.forecast`

输入是 `ct_sales_daily` 近 90 天按日求和。算法在 `ForecastEngine`：

| 方法 | 含义 |
| --- | --- |
| `MA` | 7 日滑动平均，滚动外推 |
| `SES` | 简单指数平滑，α=0.3，水平值持平外推 |
| `HOLT` | 带趋势指数平滑，α=0.3、β=0.1 |
| `SEASONAL_NAIVE` | 周期 7，取近 4 个同星期均值 |
| `AUTO` | 对上述四法做最近最多 14 天 holdout MAPE，选最小者 |

预测带 ±1.28σ 残差区间（约 80% 带宽）。每次 `run` 落 `ct_forecast`。

补货公式（仓+SKU）：

```text
horizon 内预测需求 demand
日均 daily = demand / horizon
安全库存 safety = daily × serviceDays（默认 3）
建议量 suggestQty = max(0, demand + safety − qtyAvailable)
缺货日 = 今日 + floor(qtyAvailable / daily)
```

`inTransit` 当前恒为 0。补货行可一键转成跨系统协同指令（默认 `COORDINATE_REPLENISH` → SRM + SAP + OA + WMS）。

### 6.5 沙盘 `com.ir.sandbox`

沙盘分两条路径，共用 `SandboxEngine`，但入口、参数来源和推荐方式不同。

| 类型 `kind` | 入口 | 谁设定参数 | 结果怎么用 |
| --- | --- | --- | --- |
| `BASELINE` | 启动时 `ensureBaseline()` | 默认参数 | 对比基准 |
| `MANUAL` | 人工沙盘页创建 | 计划员改需求倍率、分仓、承运、成本/效率权重 | 手工对比后「生成指令」或「立即执行」 |
| `AUTO` | `POST /api/sandbox/auto/run`，启动可选自动跑，cron 每 6 小时 | 系统策略网格 | 按综合分标 `recommended`，看板展示 |

用当前库存快照 + 日销 + 订单省份分布做基线。仓库集合为 `WH-SH / WH-BJ / WH-GZ`；WMS 库存同步时已映到这套仓号，沙盘按仓+SKU **累加** 可用量。

可调参数（`ScenarioParams`）：

- 推演天数、总需求倍率、分渠道需求倍率
- 分仓策略：`NEAREST` / `LOWEST_COST` / `BALANCED` / `SINGLE_WAREHOUSE`
- 承运商配比与费率（默认 SF 0.4 / JDL 0.3 / SELF 0.3）
- 安全天数、补货提前期、期初库存倍率
- 仓储 / 操作 / 包材 / 缺货惩罚单价
- **成本权重 / 效率权重**（默认各 0.5）

日循环：到货 → 按区域需求选仓发货 → 累计运费/操作/包材/仓储/缺货罚 → 按安全天数生成在途补货。需求外推用 `seasonalNaive`。

**综合分**（`BalanceScorer`，一批场景内相对打分）：

```text
成本分     = 总成本越低越高（min-max 反转）
效率分     = 服务水平×50% + 时效分×30% + 缺货分×20%
综合分     = 成本分×costWeight + 效率分×efficiencyWeight
```

系统自动沙盘网格（14 天 horizon）：

1. 就近分配（效率优先）
2. 最低成本
3. 成本效率均衡
4. 上海 / 北京 / 广州单仓
5. 时效承运（顺丰为主）
6. 经济承运
7. 高安全库存 + 短交期
8. 低安全库存 + 最低成本
9. 供应前置（短交期拉动）
10. ERP 物料拉动
11. 经销商备件优先

`apply?execute=` 按业务单号生成指令（不再把 SKU/承运商编码当成订单号）：

- `SINGLE_WAREHOUSE` / `LOWEST_COST` → 对未完成订单 `OMS_REROUTE_WAREHOUSE`（目标仓）
- 承运商主承运相对基线变化 → 对未签收运单 `TMS_SWITCH_CARRIER`
- 场景仍有缺货 SKU → `CoordinationService` 同时生成 `SRM_PURCHASE_SUGGEST` + `SAP_CREATE_PR` + `OA_START_WORKFLOW` + `WMS_REPLENISH`（匹配到经销商缺货/BOM 时再加 DMS/BOM）
- `execute=false`（默认）只写 `PENDING`；`true` 则立刻 `createAndExecute`

### 6.6 成本 `com.ir.cost`

读 `ct_cost_record`：按类型 / 仓 / 承运商 / 日期汇总，对照 `ct_cost_target` 做目标 vs 实际。节约金额来自状态 `SUCCESS` 的指令上的 `expectedSaving`（人工填，不是系统算出来的）。

## 7. 运动层：大脑如何动手

`ActionService` 是单条指令出口；`CoordinationService` 负责把一条业务决策拆成一组指令。`ActionEnricher` 会在落库前补全参数（例如把 SAP 库存 bizKey `MAT-1000/1000/0001` 还原成物料 `MAT-1000` 和数量）。

指令类型前缀决定落点：

| 类型 | 目标系统 | 作用 |
| --- | --- | --- |
| `OMS_REROUTE_WAREHOUSE` | OMS | 改分配仓，并回写订单快照的 `warehouseCode` |
| `OMS_HOLD` / `OMS_UNHOLD` | OMS | 挂起 / 解挂 |
| `OMS_PRIORITIZE` | OMS | 加急（HTTP 落到 remark） |
| `OMS_AUTO_PROCESS` | OMS | 一键处理 |
| `OMS_CANCEL` | OMS | 取消，快照状态改为 `CANCELLED` |
| `WMS_ALLOCATE` | WMS | 出库分配，快照状态改为 `ALLOCATED` |
| `WMS_REPLENISH` | WMS | 触发仓内 Min/Max 补货任务 |
| `TMS_DISPATCH` | TMS | 调度发车 |
| `TMS_SYNC_TRACK` | TMS | 拉轨迹 |
| `TMS_SWITCH_CARRIER` | TMS | 换承运商，回写运单快照 |
| `SRM_PURCHASE_SUGGEST` | SRM | MOCK 记成功；HTTP 调 SRM 生成采购申请草稿 |
| `SRM_SUBMIT_PR` / `SRM_APPROVE_PR` | SRM | 提交 / 审批采购申请 |
| `SAP_CREATE_PR` / `SAP_RELEASE_PR` / `SAP_RELEASE_MO` | SAP | 创建/释放采购申请，释放生产订单 |
| `BOM_EXPLODE` | BOM | 按 BOM 号展开物料清单 |
| `INV_SUBMIT_REQUEST` / `INV_APPROVE_REQUEST` | INV | 提交 / 审核开票申请 |
| `CRM_ADVANCE_STAGE` / `CRM_ESCALATE_CASE` | CRM | 推进商机、升级工单 |
| `DMS_REPLENISH_SHORTAGE` | DMS | 按经销商缺货生成补货单 |
| `OA_START_WORKFLOW` | OA | 发起通用/采购审批 |
| `OA_APPROVE_TASK` | OA | 按待办审批人完成当前节点（不新开流程） |

闭环：

```text
快照变化 ─▶ 规则/预测/沙盘 ─▶ 预警或场景
                              │
                              ▼
                     CoordinationService 分发
                              │
              ┌──────── SRM 采购建议
              ├──────── SAP 采购申请
              ├──────── OA 审批
              ├──────── WMS 仓内补货
              └──────── DMS/BOM（命中时）
                              │
                     ct_action  PENDING / SUCCESS
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        HTTP/MOCK execute               回写本地快照
```

角色：`ADMIN` / `PLANNER` 可写，`VIEWER` 只读。前端按角色藏按钮，后端仍走登录 Bearer。

## 9. 当前边界（写代码时必须当成约束）

这些不是待办清单，是 **现在这颗大脑实际长到哪**。

1. **12 系统全接入**：OMS / WMS / TMS / BMS 拉履约与成本；SRM / SAP / BOM / INV / CRM / DMS / OA 拉生态快照并接受指令。默认 MOCK；`IR_HTTP_SYSTEMS` 或界面切 HTTP 后走各系统 `GET/POST /api/open/ir/*`。OA 待办可直接 `OA_APPROVE_TASK`。
2. **以拉为主**：5 分钟 cron + 手工同步，没有 webhook / 消息总线。执行系统状态变了，大脑最多延迟一个周期。
3. **快照不是账本**：IR 改快照（取消、改仓）不会保证与源系统最终一致；源系统才是权威。
4. **仓编码已在同步时归一**：看板和沙盘用 OMS 仓号；下发 WMS 时再映回 WH01/02/03。
5. **在途补货建议仍偏粗**：补货模型的 `inTransit` 仍为 0（没有 SKU 级在途采购）。
6. **自动沙盘默认不自动执行**：`ir.sandbox.auto-apply=false`，只打推荐分；人工确认后可「立即执行」。
7. **成本节约仍依赖 `expectedSaving`**，不能当成真实 P&L。

## 11. 读完后应形成的图景

当前供应链的「身体」已经按专业系统拆开：OMS 接单、WMS 作业、TMS 在途、SRM 采购、SAP 记账、BOM 结构、INV 开票、CRM/DMS 需求、OA 审批、BMS 算钱。  
当前供应链的「大脑」是 IR：用快照做工作记忆，用规则/预测/人工沙盘/自动沙盘做判断（成本与效率兼顾），用指令反向驱动全部执行系统。
